# Benchmark Observability 合并建议（Freeze Candidate）

## 0. 最终裁决

当前科学设计已经完成，指标体系也基本完成。最后需要做的不是继续增加指标，而是把对象模型、缓存语义、成本口径、support 映射和执行可比性收口。

完成本文件列出的修改后，应停止继续优化“修改建议”，直接合并进唯一 Workplan。最终 source of truth 只保留：

- Proposal；
- Workplan；
- schemas；
- metric specification；
- tests。

本文件在合并后只作为决策记录，不再作为平行执行依据。

总原则保持不变：

主 benchmark 不变，只增加 minimal mandatory、可重建的 observability contract。

不改变：

- 数据集与 split；
- fixed-leaf 协议；
- left-deep vs canonical balanced 主比较；
- right-deep diagnostic；
- Task Quality / Plan Robustness / Lifecycle Cost 三分结构；
- 主统计检验和 GO / NO-GO；
- workload 和方法空间。

---

## 1. 已经合理并应冻结的设计

以下内容无需再改：

1. Raw artifacts 与 derived metrics 分离。
2. 所有 API 阶段共用 ModelCallAttemptRaw。
3. Provider usage 与本地 token count 分开。
4. Shared leaf、plan-specific merge、answer、judge 分阶段核算。
5. 在固定 provider、model、route 和 usage schema 下，provider usage tokens 是 operational resource accounting 的原始观测。
6. 美元费用只由可选 PricingManifest 派生。
7. Supporting labels 只在 scoring 和 run artifacts 冻结后进入分析。
8. Evidence-level diagnostics 不作为独立统计样本。
9. Embedding、entity、claimed provenance、transient live peak 等均为 optional。
10. Accepted-path work 与 observed operational work 分开报告。
11. 不将 quality、tokens、latency 合成单一总分。
12. 不将 cost per correct answer 作为主指标。

---

## 2. 与现有 Workplan 对象体系的唯一映射

Observability 不是新增一套平行 schema，而是重构和细化现有对象：

| 现有对象 | 冻结后的职责 |
|---|---|
| Plan | plan header + PlanNodeRaw |
| ViewNode | NodeArtifact |
| Run | run configuration + artifact bindings + executor configuration |
| Cost / API log | ModelCallAttemptRaw |
| Merge operation | MergeEventRaw |
| Metrics | PlanMetrics + MergeEventMetrics + EvidenceExposure + AnnotatedSupportExposure |

这样可以避免 Plan、ViewNode、Run、Cost 与新对象重复表达同一事实。

## 3. T0 只保存原始对象

### 3.1 PlanNodeRaw

PlanNodeRaw 只保存不可再推导的逻辑树事实。

字段：

- logical_node_id
- plan_id
- node_type
- leaf_id，仅 leaf node 使用
- left_logical_child_id，仅 internal node 使用
- right_logical_child_id，仅 internal node 使用
- covered_span

约束：

- leaf node 必须有 leaf_id，且没有 child IDs；
- internal node 必须有两个 child IDs，且没有 leaf_id；
- covered_span 由冻结 evidence order 定义；
- 不根据 timestamp 重新排序；
- descendant_leaf_ids、tree_level、depth_to_root、role path 和 critical path 不存入 raw schema。

如为性能缓存任何派生字段，必须显式标记 derived_cache_field，并测试它与递归 child closure 完全一致。

### 3.2 NodeArtifact

NodeArtifact 表示一个逻辑节点在某次运行中的具体物化结果。

字段：

- materialized_node_id
- logical_node_id
- run_id
- content_artifact_id
- content_hash
- artifact_kind
- memory_tokens_local
- capacity_tokens
- tokenizer_snapshot
- serialization_version
- operator_config_id
- deterministic_operator_hash，可选
- model_snapshot
- prompt_hash
- creation_event_type
- creation_event_id
- schema_version
- validation_status
- materialization_source
- response_hash
- artifact_status

说明：

- content_artifact_id 是稳定的 artifact 引用，避免把本机绝对 URI 作为科学身份；
- creation_event_type 用于区分 leaf construction、merge、deterministic render 等来源；
- creation_merge_event_id 不再作为所有 node 的通用字段；
- materialization_source 只允许 generated、cache、deterministic；
- content 必须可由 content_artifact_id 读取，否则无法复算 token、embedding 或做文本审计。

Source-dependent invariants：

Generated：

- model_snapshot、prompt_hash、response_hash 和 accepted output binding 必须存在；

Cache：

- creation_event_id 必须解析到一个 cache materialization event；
- 该 event 的 cache_source_artifact_id 必须存在；
- 本次 accepted attempt 禁止；
- model / prompt / response 字段可继承源 artifact，或按 schema 标记为 null；

Deterministic：

- deterministic_operator_hash 必须存在；
- accepted attempt 禁止；
- model_snapshot 可为 null。

### 3.3 ModelCallAttemptRaw

所有 leaf、merge、answer、judge API 调用共用一套 attempt 记录。

字段：

- attempt_id
- run_id
- stage
- logical_call_id
- accepted_attempt
- retry_index
- requested_model
- returned_model
- provider
- provider_route
- request_id
- prompt_hash
- response_hash
- local_serialized_input_tokens
- local_output_content_tokens
- tokenizer_snapshot
- serialization_version
- provider_input_tokens_total
- provider_cached_input_tokens_subset
- provider_output_tokens_total
- provider_reasoning_tokens_subset，provider 提供时
- usage_schema_version
- provider_usage_source
- scheduled_at
- started_at
- finished_at
- http_status
- finish_reason
- parse_status
- failure_type
- attempt_outcome
- status

provider_usage_source 只允许：

- provider_exact
- provider_estimated
- missing

规则：

- provider_usage_source = missing 时，所有 provider_* token fields 必须为 null；
- local_* token fields 仍可存在；
- local token 不得填充 provider_* 字段。

Provider 未返回 usage 时，不能用本地 tokenizer 数量冒充 provider_exact。

attempt_outcome 只允许：

- accepted_materialized；
- successful_nonmaterialized；
- failed_provider；
- failed_parse；
- failed_validation；
- cancelled_before_start；
- cancelled_after_start。

successful_nonmaterialized 可能已经消耗 provider tokens 和 latency，但没有进入 materialized lineage，必须计入 observed operational work。

accepted_attempt 可以保留为查询方便的派生缓存字段，但唯一真值是 AcceptedOutputBindingRaw 的引用关系。必须满足：

attempt.accepted_attempt = true
当且仅当该 attempt_id 被一个成功的 AcceptedOutputBindingRaw 引用。

如果保留该布尔字段，必须有一致性测试；否则应由引用关系在分析阶段派生。

Cached input tokens 的冻结语义：

provider_cached_input_tokens_subset 是 provider_input_tokens_total 的子集，不是额外 token。

provider_reasoning_tokens_subset 是 provider_output_tokens_total 的子集，不是额外 output token。若 provider 没有返回 reasoning usage，则该字段为 null。不同 provider 的原始语义由 provider adapter 和 usage_schema_version 归一化。

因此：

uncached_input_tokens = provider_input_tokens_total - provider_cached_input_tokens_subset

禁止计算：

provider_input_tokens_total + provider_cached_input_tokens_subset

如果 provider 的缓存或 reasoning usage 语义不同，必须由 provider adapter 通过 usage_schema_version 统一，不能由 analysis 代码猜测。

### 3.4 AcceptedOutputBindingRaw

所有会产生正式 accepted output 的阶段共用一个最小绑定对象，覆盖 leaf、merge、answer 和 judge。

字段：

- binding_id
- run_id
- stage
- logical_call_id
- accepted_attempt_id
- output_artifact_id
- binding_status

约束：

- 一个成功 binding 只能引用一个 accepted attempt；
- 一个 accepted attempt 只能被一个成功 binding 引用；
- binding 的 stage、logical_call_id 和 output artifact 必须一致；
- accepted_attempt = true 只能由成功 binding 的引用关系确定，布尔字段若保留只能作为一致性缓存。

Leaf 输出绑定到 NodeArtifact；merge 的 binding 与 MergeEventRaw 关联；answer 和 judge 分别绑定 AnswerArtifact 与 JudgeArtifact。

### 3.5 MergeEventRaw

MergeEventRaw 只保存一次逻辑 merge 与物化结果之间的关系，不重复保存 NodeArtifact 已经拥有的 token 字段。

字段：

- merge_event_id
- run_id
- logical_operation_id
- accepted_binding_id，可为 null
- left_materialized_node_id
- right_materialized_node_id
- output_materialized_node_id
- output_budget
- materialization_source
- cache_source_artifact_id，可为 null
- event_status

约束：

Generated：

- accepted_binding_id 必须存在；
- binding stage 必须为 merge，且恰好指向一个 accepted ModelCallAttemptRaw；
- binding output_artifact_id 必须与 output_materialized_node_id 一致；
- cache_source_artifact_id 必须为 null。

Cache：

- accepted_binding_id 必须为 null；
- 不得伪造 ModelCallAttemptRaw；
- cache_source_artifact_id 必须存在。

Deterministic：

- accepted_binding_id 必须为 null；
- cache_source_artifact_id 根据实现可为 null；
- 不计入 generative rewrite operator。

一个 logical call 不得有两个成功 accepted bindings。

Failed attempts 不得进入 materialized lineage。

## 4. Run 必须冻结执行策略

Wall-clock 只有在执行策略一致时才可比较。

Run 增加：

- executor_config_hash
- executor_mode
- concurrency_limit
- cache_mode
- rate_limit_policy_hash
- retry_policy_hash
- provider_route
- run_started_at
- run_finished_at
- replication_index
- execution_order_index
- run_batch_id
- provider_observation_window

正式 topology 比较必须使用：

- cold-cache；
- same executor；
- same concurrency limit；
- same retry policy；
- same rate-limit policy；
- same provider route。

Warm-cache 和 resume 结果只作为恢复效率审计。

不要求 concurrency limit 必须为 1。Balanced 可以利用其结构允许的并行性，但所有 topology 必须处在同一执行规则下。

正式 latency 比较还必须：

- 对 topology 的执行顺序随机化或交替化；
- 在 calibration 或 formal protocol 中冻结重复次数；
- 主要报告 median 和 episode-clustered uncertainty interval；
- 对服务端负载敏感时补充 p90 / p95；
- 将 provider_observation_window 作为解释 latency 的上下文，而不是隐藏变量。

Wall-clock 的阶段边界也必须冻结：

- 阶段起点：该阶段首个 logical operation 被 scheduled；
- 阶段终点：该阶段最后一个 required artifact 被验证并持久化；
- 包含 retry backoff、网络等待、本地序列化和 artifact 写盘；
- 不将不同阶段的时间混在同一个 total_wall_clock 中。

至少记录：

- leaf_wall_clock；
- merge_wall_clock；
- answer_wall_clock；
- judge_wall_clock。

正式 topology construction 使用 merge_wall_clock；marginal end-to-end 使用 merge_wall_clock + answer_wall_clock；完整 pipeline 再加 leaf_wall_clock。Judge wall-clock 单独报告。

## 5. T6 派生 PlanMetrics

PlanMetrics 由 PlanNodeRaw 递归计算，不调用模型。

字段：

- descendant_leaf_ids
- leaf_depth_vector
- order_role_path_vector
- tree_height
- critical_path_merge_count
- merge_count
- deterministic_plan_hash

命名修正：

- temporal_role_sequence 改为 order_role_sequence；
- earlier_child_fraction 改为 earlier_span_fraction；
- later_child_fraction 改为 later_span_fraction；
- structural_critical_path 改为 critical_path_merge_count。

## 6. T7 最小必选机制指标

Phase 1 必选仍只保留四类。

### 6.1 结构暴露

指标：

- leaf_depth
- generative_rewrite_depth
- order_role_sequence
- earlier_span_fraction
- later_span_fraction
- relative_position

定义：

generative_rewrite_depth 表示一条 evidence 到最终 root 在语义路径上经过多少个 generative merge operators。

它不受以下因素影响：

- cache hit；
- retry；
- failed attempt；
- API 是否在本次进程执行。

物理执行单独使用：

- accepted_materialized_generation_count
- failed_api_attempt_count
- cache_hit_count

### 6.2 压缩暴露

指标：

- content_to_budget_pressure
- pressure_sum
- pressure_max
- actual_compression_ratio
- output_budget_utilization

计算：

content_to_budget_pressure = (left NodeArtifact.memory_tokens_local + right NodeArtifact.memory_tokens_local) / B_merge

actual_compression_ratio = output NodeArtifact.memory_tokens_local / (left memory tokens + right memory tokens)

output_budget_utilization = output NodeArtifact.memory_tokens_local / B_merge

pressure_sum 和 pressure_max 在 evidence 的 generative path 上聚合。

Payload 负载另记为：

payload_to_budget_ratio = ModelCallAttemptRaw.local_serialized_input_tokens / B_merge

content_to_budget_pressure 只是节点内容相对于固定输出预算的结构代理，不证明实际 semantic retention 或信息压缩程度。

payload_to_budget_ratio 是序列化后的完整 API 输入负载相对于预算，不能与 content_to_budget_pressure 混称。

### 6.3 合并平衡

指标：

- token_imbalance_abs
- token_imbalance_signed
- time_span_imbalance，optional-if-available

计算：

token_imbalance_abs = abs(left memory tokens - right memory tokens) / total child memory tokens

token_imbalance_signed = (left memory tokens - right memory tokens) / total child memory tokens

time_span_imbalance 只有在时间字段完整、含义稳定时报告；否则为 unavailable，不能强行补值。

signed imbalance 只在以下顺序合同成立时解释：

- left child 总是覆盖较早的 frozen evidence span；
- right child 总是覆盖较晚的 frozen evidence span；
- order-preserving plan 不交换左右 child；
- span 不可比较或重叠时 signed imbalance 为 unavailable。

token_imbalance_abs 是主要平衡指标；signed 版本只作为 order-position diagnostic。

### 6.4 资源与执行

资源指标必须真正分成 accepted-path 和 observed operational 两套字段。

Accepted-path：

- shared_leaf_input_tokens_total
- shared_leaf_cached_input_tokens_subset
- shared_leaf_uncached_input_tokens
- shared_leaf_output_tokens
- accepted_merge_input_tokens_total
- accepted_merge_cached_input_tokens_subset
- accepted_merge_uncached_input_tokens
- accepted_merge_output_tokens
- accepted_answer_input_tokens_total
- accepted_answer_cached_input_tokens_subset
- accepted_answer_uncached_input_tokens
- accepted_answer_output_tokens

Observed operational：

- observed_leaf_input_tokens_total
- observed_leaf_cached_input_tokens_subset
- observed_leaf_uncached_input_tokens
- observed_leaf_output_tokens
- observed_merge_input_tokens_total
- observed_merge_cached_input_tokens_subset
- observed_merge_uncached_input_tokens
- observed_merge_output_tokens
- observed_answer_input_tokens_total
- observed_answer_cached_input_tokens_subset
- observed_answer_uncached_input_tokens
- observed_answer_output_tokens
- api_attempt_count
- failed_api_attempt_count
- successful_nonmaterialized_attempt_count
- accepted_materialized_generation_count
- cache_hit_count
- retry_token_overhead
- retry_latency_overhead
- sum_attempt_latency
- critical_path_elapsed_latency
- parallelism_factor

关系：

For provider token work:

Observed work = accepted work + successful nonmaterialized work + failed-after-provider-execution work

accepted_materialized_generation_count + successful_nonmaterialized_attempt_count
= provider-executed successful attempts

Cache hit 不产生 provider usage，但增加 cache_hit_count。

所有 uncached 字段必须满足：

uncached_input_tokens = input_tokens_total - cached_input_tokens_subset

论文主表可以只展示 total input/output；原始 CSV 和 artifact 必须保留 total、cached subset、uncached 三项。

Judge overhead 使用同一 total / cached subset / uncached 结构，但单独归档，不并入 memory lifecycle cost。

结构与运行：

- logical_merge_count
- critical_path_merge_count
- total_wall_clock

定义：

- elapsed wall-clock = 该阶段最后一个 required artifact 持久化时间 - 首个 logical operation scheduled 时间；
- sum_attempt_latency = 所有已开始 attempts 的 execution latency 之和；
- operation_elapsed_latency = artifact_persisted_at - logical_operation_scheduled_at；
- critical_path_elapsed_latency = 依赖 DAG 上 operation_elapsed_latency 权重之和的最长路径；
- parallelism_factor = sum_attempt_latency / elapsed wall-clock。

operation_elapsed_latency 包含排队、retry、backoff、provider latency、parsing、validation 和 artifact persistence。elapsed wall-clock 反映用户可见阶段完成时间，sum_attempt_latency 与 parallelism_factor 反映累计服务工作和并行化效果。它们不替代 critical_path_merge_count，而是与其分开报告。

## 7. 状态成本的冻结定义

删除模糊的 durable_state_tokens，拆为三类。

### 7.1 Deployment state

真实系统查询或继续更新必须保留：

- deployment_memory_tokens
- deployment_metadata_bytes
- deployment_capability_profile
- deployment_state_measurement_protocol

deployment_capability_profile 只允许：

- FINAL_QUERY_ONLY
- FINAL_QUERY_AND_APPEND
- PREFIX_QUERY_AND_APPEND
- FULL_ONLINE_RECOVERY

Phase 1 primary offline 默认使用 FINAL_QUERY_ONLY；online secondary 若启用 prefix continuation，则使用 PREFIX_QUERY_AND_APPEND。具体值必须写入 protocol，不得由不同 topology 自行选择。

例子：

- eager left-deep：当前 published root；
- online balanced：当前 live forest；
- periodic reconstruction：当前 published root 和必要 source handles。

Primary Pareto 使用 deployment_memory_tokens，而不是实验目录大小。

deployment state 的定义是：为维持 benchmark 声明的在线功能，包括查询、继续追加、指定更新语义和恢复语义，系统必须保留的最小运行状态。

Phase 1 必须先冻结 capability profile。若 primary 只要求 final query，则只比较 final-query profile；若 online track 要求 prefix query 或 continuation，则所有 online topology 必须使用同一 profile。不得对一个 topology 只保留 root、对另一个 topology 保留可继续更新所需的完整 state。

测量时点必须冻结：

- primary offline：所有 k 个 leaves 已处理、final view 已发布、answer generation 之前；
- online secondary：按 prefix t 记录 deployment_memory_tokens(t)；
- online summary：报告 final、mean prefix、peak prefix 三个值。

如果 Phase 1 不运行完整 online state curve，至少必须保留 primary offline 的唯一测量时点。

### 7.2 Shared source state

所有 plan 共同依赖：

- shared_leaf_tokens
- shared_raw_evidence_bytes

单独报告，不计入 plan-specific 增量状态。

### 7.3 Experiment artifact footprint

只为审计和复现保存：

- artifact_cache_bytes

包括 intermediate nodes、raw API responses、logs、judge cache 和 checksums。

它不是部署成本，不进入方法 lifecycle deployment cost。

## 8. 成本与价格口径

在固定 provider、model、route 和 usage schema 的正式 topology 比较中，provider-reported usage 是 operational resource accounting 的主要真值。它不是跨 provider、跨模型都同质的物理资源单位；跨模型或跨 provider 的 token totals 必须分层报告。

本地 token count 用于：

- capacity；
- content-to-budget exposure；
- payload 复现；
- output memory 长度。

美元费用只由可选的 run-level PricingManifest 派生。

PricingManifest 至少记录：

- pricing_manifest_id
- pricing_manifest_sha256
- provider
- model
- currency
- effective_date
- source
- source_accessed_at
- source_snapshot_hash
- uncached_input_usd_per_million
- cached_input_usd_per_million
- output_usd_per_million
- request_fee_usd

美元估算：

estimated_api_cost_usd =
[
  uncached_input_rate × (input_total - cached_subset)
  + cached_input_rate × cached_subset
  + output_rate × output_tokens
] / 1,000,000
+ request_fee × request_count

所有 token rate 的单位固定为 USD per 1M tokens。其他 provider 的价格单位必须在 provider adapter 中归一化，通用 cost calculator 不负责猜测单位。

不要求每个调用保存 pricing snapshot、currency 或 pricing formula version。

以下仅用于实验管理：

- provider_reported_cost_usd
- actual_billed_cost_usd

它们不作为方法比较的 source of truth。

成本按四阶段报告：

1. Shared leaf construction
2. Plan-specific merge construction
3. Answer / query
4. Judge / evaluation overhead

Judge overhead 不计入 memory 方法的 lifecycle deployment cost。

同时报告：

Marginal topology resource cost：

- accepted merge work + accepted answer work

End-to-end resource cost：

- shared leaf construction + marginal topology work

正式主展示：

- quality–token Pareto
- quality–latency Pareto

Estimated USD 仅作 optional deployment-facing view。

## 9. Supporting annotation 访问与映射合同

### 9.1 Protected label store

Protected label store 保存：

- gold_answer
- supporting_evidence_ids

访问约束：

- constructor package 不得依赖；
- plan generator 不得导入；
- merge serializer 不接受 label 字段；
- analysis job 只能在 run artifacts 和 score 冻结后显式加载；
- 所有加载写 access log。

访问边界按阶段冻结：

ConstructionInputView：

- 可访问 raw evidence、leaf configuration 和 plan；
- 不可访问 query、gold、support annotations。

AnswerInputView：

- 可访问 final memory、query 和 answer configuration；
- 不可访问 gold、support annotations。

ScoringInputView：

- 在 run artifacts 和 answer 冻结后，才可访问 gold、support annotations 和 evaluator。

不要求一定建立三套数据库，但 serializer 和类型/接口边界必须实现这三种白名单。

### 9.2 Annotation 到 leaf 的映射

冻结映射链：

supporting session → atomic evidence → chunk → leaf

每条 annotation 记录：

- support_mapping_status
- mapped_evidence_ids
- mapped_chunk_ids
- mapped_leaf_ids

support_mapping_status 只允许：

- exact
- expanded_to_chunks
- unresolved

保留逐 annotation 的 SupportEvidenceExposure。

正式 summary 默认按 unique supporting leaves 聚合，避免多个 annotations 落到同一 leaf 后重复加权。

报告 unresolved mapping 数量和比例。

## 10. Secondary diagnostics 的统计规则

Eval-protocol-v1.0 中，机制指标默认是描述性的。

冻结规则：

- 每个 episode-plan-run 内先聚合；
- topology 间做 episode-level paired contrasts；
- 报告 episode-clustered bootstrap intervals；
- evidence-level 行不作为独立样本；
- 不将不同 topology 的第 n 个 merge 直接配对；
- source features 与 materialized mediators 分开；
- 不使用 post-treatment mediator 回归声称因果；
- 机制指标不进入 primary GO / NO-GO；
- 机制指标不产生 confirmatory p-values。

建议写入协议：

In eval-protocol-v1.0, mechanism diagnostics are descriptive and report episode-clustered bootstrap intervals only; they do not produce confirmatory p-values.

主 topology effect 继续使用正式 permutation test。

未来若需要机制回归或 confirmatory mechanism claims，另行作为 v1.1 或论文分析计划预注册。

## 15. Proposal 建议文字

英文：

In addition to measuring topology-induced behavioral differences, the benchmark records preregistered, fine-grained observability variables at plan, merge, node, and evidence levels, including generative rewrite depth, content-to-budget exposure, merge-partner balance, order-role exposure, and resource usage. These variables are reconstructed from raw run artifacts and used only as descriptive secondary diagnostics with episode-clustered uncertainty intervals. They are never used to select episodes, tune prompts or budgets, generate plans, adapt construction policies, or produce confirmatory mechanism claims.

中文：

除了测量 topology 引起的行为差异，本 benchmark 还在 plan、merge、node 和 evidence 粒度记录预注册的可观测变量，包括生成式重写深度、内容相对预算暴露、合并对象平衡、顺序角色暴露和资源用量。这些变量由原始运行产物事后重建，仅作为带 episode-clustered 不确定性区间的描述性 secondary diagnostics，不用于筛选 episode、调整 prompt 或 budget、生成 plan、自适应构造策略，亦不用于提出确认性机制结论。
